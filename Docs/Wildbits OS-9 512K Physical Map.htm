System RAM — who owns what at run time

BlocksOwnerContents
$00Kernel (permanent)The system block: D.* globals page, the 8K-block allocation map at $0200 (one byte per physical block, up to 2MB), system/user dispatch tables, kernel data — and the boot trampoline at $0600 (below). Marked used by the memory-sizing routine itself.
$01–$03Free poolGeneral allocation. (Block 1 doubles as bootos9’s temporary MMU copy window during a re-boot, then returns to the pool.)
$04–$07Boot modulesOS9Boot is loaded into the blocks just below block 8 — blocks (8−n)…7 for an n-block bootfile (currently n=4, so $04–$07). The kernel (last module in the merge) lands in the top block and is marked used; the rest hold the boot module directory contents.
$08–$3FFree pool (448K)Process address spaces, RBF/SCF buffers, bitmap framebuffers (VICKY fetches these over its RAM port — the layers you see in view/shellbg live here), and rbmem’s 8K flash-write cache (one block via F$AllRAM at Init).

Memory sizing is a ghost test, not a table: the kernel writes a marker through successively doubled block numbers (8, 16, 32, 64…) until the write aliases back to block 0 — on these machines that stops at 64 blocks = 512K, recorded in D.MemSz. Nothing about the pool is hard-coded; more RAM would be found the same way.

The trampoline

When bootos9 (re)boots the system, running code is about to yank the MMU out from under itself. The escape: it copies a tiny relocatable stub to $0600 in block 0 (RELOC_ADDR), jumps to it, and the stub — running from an address that stays mapped — resets MMU slots 0–7 to identity (blocks 0–7), then jumps to the kernel entry point found in the freshly-loaded bootfile. The same staging is used by the FEU’s os9boot. That stub, plus the block $04–$07 staging area, is the entire hand-off mechanism between boot stages.

The boot chain, block by block

  1. Power-on → Booter (flash $7D–$7F, the top 24K of the chip — the three booter_*.bin pieces fnxmgr installs).
  2. Booter → FEU OS-9: loads the mini system from /f0 (flash $78–$7C, the five f0_*.bin pieces, 40K). FEU = “First Executable Unit” — a self-contained Level 2 OS-9 living entirely in flash.
  3. FEU startup → bootos9 /s0/OS9Boot: the FEU’s startup script chains to the real system — bootos9 reads the SD card’s OS9Boot into RAM blocks (8−n)…7 through the block-1 copy window.
  4. Trampoline: stub at $0600, MMU identity map, jump to kernel — full OS-9 running from SD-loaded RAM. The FEU’s flash blocks return to being just the /f0 drive.

Flash — one chip, three tenants

BlocksSizeRole
$40–$77448K/f1 — the user flash drive (formattable, writable; rbmem erase/program with DQ6 polling).
$78–$7C40K/f0 — the FEU system image; mounted read-only at run time. fnxmgr’s bulk.csv flashes these as chip sectors $38–$3C.
$7D–$7F24KBooter — first code after reset; chip sectors $3D–$3F.

EXRAM / cartridge ($80–$9F)

One decode, different hardware per machine: on the K2 this is the 256K expansion RAM (physical $10_0000–$13_FFFF). On the Jr2 the same select reaches the cartridge port: /c0 is based at block $80 and /c1 at $90 (flash cartridges, same SST39 family and driver as onboard flash). This region shares the external bus — and its single write strobe — with the flash chip and the RTC, which is why the v8_rc6 core’s strobe policy covers all three.
