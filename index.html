1The translation pipeline

Every CPU access goes through one of eight 8K slots. The slot’s LUT entry supplies the physical block; the entry’s top bits pick which bus answers.

CPU address

A15..A13 selects one of 8 slots; A12..A0 is the 8K offset. Fixed I/O at $FDxx–$FFxx bypasses translation.

→

MMU LUT entry

4 LUTs × 8 slots × 8 bits. Active LUT = $FFA0[1:0]. Slot registers at $FFA8–$FFAF read/write the LUT selected by $FFA0[5:4].

→

Physical bus

Entry prefix routes to RAM, the flash window, expansion RAM, or a sectored I/O page. Block number becomes the high address bits.

5Boot: from reset to shell

Reset — boot mode. The MMU comes up with slots 0–6 identity-mapped to RAM and slot 7 pointed at flash block $7F (verified in the LUT reset values), so the 6809’s vectors at $FFFE fetch from the top 8K of the flash window: the FEU.

FEU runs from flash. The Flash Environment Utility (living in blocks $78–$7F, with its file area visible to OS-9 later as /f0) initializes hardware, shows its menu, and executes its startup script: bootos9 /s0/OS9Boot.

bootos9 loads the bootfile. OS9Boot is read from the SD (or DriveWire) volume into RAM. The loader requires krn to be the final module, anchored exactly 4096 bytes before end-of-file — break that and you get “can’t locate the kernel in the bootfile.”

Kernel takes over. krn (at Bt.Start = $EE00) copies DisTable to D.Clock, plants the LowSub trampolines at $0160, shadows the constant page at $FD00, clears boot mode so slot 7 becomes RAM, and walks the module chain: ioman, file managers, drivers, clock.

sysgo → startup → shell. sysgo forks the shell (loading the merged SHELLMODS pack), startup runs (load utilpak1 / link shell / iniz wz), and the console is yours.

Memory sizing is a ghost test, not a table: the kernel writes a marker through successively doubled block numbers (8, 16, 32, 64…) until the write aliases back to block 0 — on these machines that stops at 64 blocks = 512K, recorded in D.MemSz. Nothing about the pool is hard-coded; more RAM would be found the same way.

The trampoline

When bootos9 (re)boots the system, running code is about to yank the MMU out from under itself. The escape: it copies a tiny relocatable stub to $0600 in block 0 (RELOC_ADDR), jumps to it, and the stub — running from an address that stays mapped — resets MMU slots 0–7 to identity (blocks 0–7), then jumps to the kernel entry point found in the freshly-loaded bootfile. The same staging is used by the FEU’s os9boot. That stub, plus the block $04–$07 staging area, is the entire hand-off mechanism between boot stages.

The boot chain, block by block

  1. Power-on → Booter (flash $7D–$7F, the top 24K of the chip — the three booter_*.bin pieces fnxmgr installs).
  2. Booter → FEU OS-9: loads the mini system from /f0 (flash $78–$7C, the five f0_*.bin pieces, 40K). FEU = “First Executable Unit” — a self-contained Level 2 OS-9 living entirely in flash.
  3. FEU startup → bootos9 /s0/OS9Boot: the FEU’s startup script chains to the real system — bootos9 reads the SD card’s OS9Boot into RAM blocks (8−n)…7 through the block-1 copy window.
  4. Trampoline: stub at $0600, MMU identity map, jump to kernel — full OS-9 running from SD-loaded RAM. The FEU’s flash blocks return to being just the /f0 drive.

EXRAM / cartridge ($80–$9F)

One decode, different hardware per machine: on the K2 this is the 256K expansion RAM (physical $10_0000–$13_FFFF). On the Jr2 the same select reaches the cartridge port: /c0 is based at block $80 and /c1 at $90 (flash cartridges, same SST39 family and driver as onboard flash). This region shares the external bus — and its single write strobe — with the flash chip and the RTC, which is why the v8_rc6 core’s strobe policy covers all three.

How the split works

The CPU’s 64K space is divided into eight 8K slots, each translated through an MMU look-up entry. A single inhibit term overrides that translation for the top pages:

RegionClassBehavior
$0000–$FCFFMMUTranslated through the active LUT entry for its slot. The entry’s high bits pick the physical target (see encoding below).
$FD00–$FDFFConstant RAMWhen $FFA1 bit 0 = 1, a dedicated internal RAM page supersedes whatever the MMU maps there. Bit 0 = 0 (the reset state): ordinary MMU space.
$FE00–$FEFFFixed I/OAlways the fixed I/O page — never RAM, regardless of MMU contents.
$FF00–$FF9FFixed I/OAlways fixed I/O.
$FFA0–$FFAFMMU regsThe MMU’s own control and slot registers (decoded as $FFAx).
$FFB0–$FFEFFixed I/OAlways fixed I/O (includes the text controller at $FFC0).
$FFF0–$FFFFConstant RAMThe 6809 interrupt-vector page. When $FFA1 bit 1 = 1, a dedicated internal RAM page supersedes MMU RAM/flash. Bit 1 = 0 (reset state): vectors come from MMU space (RAM or flash).

The constant-RAM pages — what makes them special

Both switchable pages ($FD00–$FDFF and $FFF0–$FFFF) are physically separate internal RAM, not part of the MMU-managed block RAM. Three properties follow:

•  While enabled, they are visible at the same addresses in every task and every LUT — remapping slots never moves or hides them. That is what makes the vector page usable for interrupt dispatch across task switches.
•  RESET clears both enable bits, so the pages disappear from the map after a reset until software sets $FFA1 again — but their contents are retained until power-off. Values written before a reset are still there when the page is re-enabled.
•  They supersede reads and writes: with a page enabled, nothing behind it (MMU RAM or flash) can be touched at those addresses.

Group 3 is why K2 keyboard freezes intersected with the WizFi driver. The optical keyboard’s IRQ line is literally the FIFO-empty flag (OpticalKeyboardScanner.v:46), so bit 2 latches into PENDING_3 on every keystroke and nothing in the OS ever services or clears it — keydrv_k2 polls the FIFO off the 60 Hz clock and never touches the INT registers. It stays harmless only because MASK_3 resets to all-ones. Meanwhile wizfi’s F$IRQ poll entry matches against the same shared register. wildbits.d’s “not used” comment on this group is exactly the documentation gap that let that interaction hide.

Controller behavior (applies to all four groups)

  • Reset defaults: POLARITY = $00 (falling edge), EDGE = $FF (edge mode), MASK = $FF (all masked), PENDING = $00. These reset only on FPGA reset — a soft reboot preserves them, so mask bits a driver unmasked (e.g. wizfi’s group-3 bits) survive into the next OS boot.
  • PENDING latches unconditionally: pending <= pending | irq_event — the mask gates only the CPU IRQ output (Interrupt[n] = pending[n] & ~mask[n]), never the latch.
  • PENDING is write-1-to-clear; reads are side-effect-free. MASK is a plain read/write register.
  • OS init gap: the clock module clears/masks only groups 0 and 1 at init (and with a read-modify-write on MASK_0 on the campaign branches — the committed freeze fix on wb/sd_dw makes it an absolute store). Groups 2 and 3 are never initialized by the OS.

  • Delete the “not used” comments on the group 2/3 register equates.
  • Fix INT_SDC_INS to %10000000.
  • Group 0: add INT_DMA %01000000.
  • Group 2: add equates for NET (%00010000), WiFi module pin (%00100000), HDMI (%01000000).
  • Group 3: add INT_MIDI_RX %00000010, INT_OPT_KBD %00000100, INT_WIZNET %00001000, INT_MIDI_VS_RX %00010000; note K2-only on the keyboard bit.
  • Correct the INT_VIA1 comment: F256K mechanical keyboard only — the K2 optical keyboard is group 3 bit 2.

How the engine works

Sprites are line-buffered, not framebuffered. The display runs 640×480 with every 320×240 pixel doubled, so the engine only needs each sprite line once per pair of scanlines. On every odd scanline, during horizontal blanking, the master video scheduler enters its sprite phase (DoSpriteHere), hands VRAM channel 3 to the sprite state machine, and fires it.

The sprite state machine then walks all 128 attribute records, from sprite 127 down to sprite 0. For each record it checks two things in two clocks: the per-sprite enable bit, and a line hit — whether the upcoming pixel row falls inside the sprite’s vertical span. Misses cost ~3 clocks each; a full scan of 128 disabled sprites completes in under 4 µs, well inside blanking. On a hit, the engine multiplies the row-within-sprite by the sprite’s line width, adds the pixel base address, and streams that one line of pixels (8–32 bytes, fetched 16 bits at a time) from video RAM into the sprite line buffer at horizontal position X. Because sprite 0 is written last, it wins overlaps.

During the following even scanline, the compositor reads the line buffer back at pixel rate and merges it with text, bitmap, and tiles according to the master control register. A non-zero pixel index is looked up in the sprite’s selected CLUT; index 0 lets the layers behind show through.

Minimum recipe — a green 8×8 sprite at screen center

Five register groups, one interrupt-masked window. Verified end-to-end by sprtest on both machines. This is the direct-MLUT method: until the kernel’s F$MapBlk fix lands, user-mode code must program the MLUT itself, because the kernel rewrites the slot registers from its own map images on every task switch — an unprotected mapping evaporates within one timeslice (which is also why debug pokes can never do this).

  1. Prepare pixel data (no masking needed) — fill a 64-byte buffer in RAM you own with $01 (pixel index 1) and compute its physical address: block# × $2000 + offset. The buffer must outlive the sprite — a process’s pages are recycled at exit, so stay resident or use memory you keep.
  2. Enter the masked window — orcc #IntMasks. Everything touching $FFA0, the slot registers, or the mapped window sits inside one masked stretch.
  3. MLUT setup — read $FFA0, save it, write it back with bits [5:4] (EDIT map) copied from bits [1:0] (ACTIVE map) — otherwise slot writes edit somebody else’s map. Save slot 5 ($FFAD, window at $A000) and write $C1 into it.
  4. Palette (page $C1) — LUT0 entry 1 at window+$1004: write $00, $FF, $00, $00 (B, G, R, A) — pure green.
  5. Sprite record (page $C0) — write $C0 to $FFAD; sprite 0’s record is at window+$1300, eight bytes, big-endian fields:
    OffsetValueMeaning
    +0$61enable + 8×8 (size 11) + LUT0 + depth 0
    +1..+3addr hi, mid, lophysical address of the pixel buffer
    +4, +5$00, $BCX = 188  (center: 32 + (320−8)/2)
    +6, +7$00, $94Y = 148  (center: 32 + (240−8)/2)
    If the other 127 records can’t be trusted (power-on garbage can carry stray enable bits), zero $1300–$16FF first.
  6. Leave the window — restore $FFAD, restore $FFA0, andcc #^IntMasks. Total masked time: microseconds.
  7. Enable the layer — $FFC0 is fixed I/O: no mapping, no masking, any map, any time. Read it, OR in $26 (graphics $04 + overlay $02 + sprite $20, preserving the text bit), write it back. The green square appears at center.

To hide the sprite later: clear bit 5 of $FFC0 (no mapping needed), or clear the record’s enable bit (needs the mapped window again). The complete working implementation of this recipe is the sprtest command source: level1/wildbits/cmds/sprtest.asm.

Resolution — 2026-08-31, both machines verified on rc7

CLOSED sprtest v6 shows a solid 32×32 sprite at commanded center with a fully intact record readback on the K2 (turbo included) and the Jr2. The invisibility was four stacked defects, each masking the others:

  • RecodedAddy latch (RTL, the killer): in both machines’ IO page files, the sprite page recode read case (IO_Sectored_Full_Addy_i[9:0]) against 2-bit case items with no default — never matching at sprite offsets, inferring a glitch-fed latch that steered CPU writes and readbacks of the attribute BRAM into placement-dependent random quarters. Fix: selector [9:8] (rc7). This also caused the lying readback bytes and the sprites’ junky top rows.
  • Missing handoff registers (RTL): the 128-sprite rework fed the encoder’s 200MHz line-buffer write port from combinational signals; the shipping 65C02 parent (K2C_16bitsRAM_RevB3B) registers data/WE/address through 100MHz flops first. Ported into Sprite_State_Machine.v (rc7), keeping the 6809 big-endian record format.
  • OS map bug (open): user-mode F$MapBlk mappings never reach the active MLUT map on this port ($FFA0 splits active[1:0]/edit[5:4] — F256 semantics, not GIME task semantics), so mapped access aliases into plain RAM: reads and writes look consistent while corrupting live buffers — the source of every phantom “junk sprite” and false readback in the early investigation. Debug-poked mappings additionally evaporate at the next task switch. sprtest works around it with direct MLUT programming (IRQs masked, edit=active). Kernel fix pending.
  • Demo record format (open): demos written to the official little-endian F256 layout put sprites at absurd coordinates on the big-endian 6809 rework — they need migration to the layout in this report.

Verification tool: sprtest (CMDS on both l2win disks) — clears all 128 records, draws a solid 32×32 at center from its own buffer, prints S0/R/W evidence, stays resident until a keypress. Remaining cosmetics: Jr2 boot-logo junk patches (pre-existing), and the K2’s VID↔100A crossing still closes by placement luck on rebuilds (bound recommended).

How the hunt unfolded — a post-mortem

The investigation ran 2026-08-30 through -31 and was misdirected for most of a day because the four defects masked each other — every experiment’s result was the product of several bugs at once. The false trail, in order: debug-poke smoke tests appeared to write sprite records and read them back (in truth the pokes aliased into plain RAM: the MLUT mapping both edited the wrong map and evaporated at the next task switch); a diagnostic core’s trace register appeared to read $FF = “whole engine firing” (in truth the bus default); RAM debris from those very pokes rendered on-screen and was mistaken for sprite output twice. Meanwhile the real latch bug sat in plain sight — read twice and mentally auto-corrected to its obvious intent.

What broke the case: byte-level archaeology against the May snapshot and the shipping 65C02 parent cores (which surfaced the missing handoff registers), a self-verifying resident test program (sprtest) replacing all poke-based testing, and finally cold-eyed re-reading of the decode — the [9:0] selector. Lessons now baked into procedure: lint the suspect block for inferred latches before differential debugging; a simulation that stubs a block proves nothing about that block; on Level 2, register pokes to mapped hardware are meaningless from debug; and a screen photo outranks a plausible theory.
